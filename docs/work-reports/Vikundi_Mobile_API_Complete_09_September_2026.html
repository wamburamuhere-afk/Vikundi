3What's new this round

Three modules, thirty endpoints — the last of the app's administrative scaffolding, closing out the plan.

Communication

An in-app inbox every member already has — open to everyone, not just leadership. Sending a message, an SMS, or an email stays a leadership action, same as it is today. The AI assistant is built and wired in, ready for the moment a provider is configured in Settings; until then it tells the user honestly that it isn't set up yet, rather than pretending to work.

Settings & Roles

Everything an Administrator needs to manage user accounts, hand out permissions role by role, and configure the system — opened rarely, by one or two people, never by an ordinary member. Creating a full database backup, and downloading one, now both work from the phone as well as the browser. There is deliberately no way to delete a user account from the app at all.

Profile

A member's own "My Account" page — name, phone, email, a profile photo, a password change, and display/notification preferences. The smallest of the three, and the only one open to every member rather than leadership.

4Defects found in the existing system this round

The same pattern as every round so far: building each doorway means reading exactly how the web system enforces its rules, and that reading keeps finding places where it doesn't. Two findings this round were more serious than usual, and were fixed and put live as their own emergency release, ahead of and separate from this round's new features.

Any signed-in user could read the group's email and SMS passwords in plain text, and rewrite them. The System Settings page's permission check had been broken since it was written — it called on a piece of the system that no longer exists, so the check silently never ran at all. Any ordinary member, not just an administrator, could open the page and see the live email and SMS sending passwords, and could submit changes to them, to the group's security settings, and could switch off the system's own audit trail. Found before it could be exploited and fixed as an emergency release, ahead of this round's other work, and confirmed closed on both the live site and the demonstration site the same day.
A forged link could change a signed-in member's password without their knowledge. The "My Account" page's password-change form had no protection against a well-known trick where a malicious website submits a hidden form on a visitor's behalf, using whatever session happens to be open in their browser at the time. Closed the same way the rest of the system already protects every other form.
Any signed-in member could send a message to anyone in the group. The message center's send button was hidden from ordinary members in the browser, but the page behind it never actually checked who was allowed to press it — a member could still trigger a send directly. Fixed on both the phone app and the website at the same time, and the button itself is now hidden correctly for anyone without permission to use it.
Two more system-backup doorways had the same weak check already fixed elsewhere in the system. They only confirmed someone was logged in, not that they were actually allowed to touch backups — meaning any member could have deleted a backup file outright. Brought in line with the rest of the backup system, which already checks properly.
Two group leadership roles — secretary and treasurer — could change any member's role, including promoting someone to full Administrator. That level of change is now restricted to the Administrator and Chairperson only, matching the rule the main "edit member" screen already enforced — the looser rule lived only in a secondary quick-action button.
A permission mix-up was found and corrected the same day, before it reached the app. While double-checking the settings fix above, one ordinary member account was found to have been quietly granted the ability to trigger a full database backup — not because of any weakness in the phone app, which was never affected, but because of a single incorrect setting left over on the account itself. Traced to its exact cause and corrected. Standard practice on this project is to verify every finding against the live server under a real account before calling it closed; that is exactly what caught this one.
