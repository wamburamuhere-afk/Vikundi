1What changed since the last report

The last report covered the financial ledger and expenses/petty cash. Since then, two more modules are finished: budgets (planning a spend before it happens, with a line-by-line breakdown, and its own review→approve→reject sign-off), and member payouts — recording one-off assistance paid directly to a member, the simplest screen in the app: no sign-off chain at all, just a record the moment it happens.

The number that matters. Every financial screen the group runs on — savings, fines, bereavement support, the ledger, reconciliation, expenses, petty cash, budgets and payouts — is now finished, deployed and documented. 66 of roughly 117 planned doorways are finished. What is left is entirely group administration used occasionally rather than routinely — meetings, documents, elections, messaging — plus the settings screens an administrator rarely opens.

3Defects found in the existing system

The same pattern as every report so far: building each doorway means reading exactly how the web system enforces its rules, and that reading keeps finding places where it does not. Budgets was the worst yet — of seven files behind that one screen, only two checked any permission at all.

Any signed-in user could approve any budget directly — skipping review entirely. The action behind the budget screen's own “Reject” button had no permission check whatsoever, and separately let the caller set a budget's status straight to “approved” without going anywhere near the actual approve step or the person who is supposed to sign off on it.

Closed by restricting that action to exactly what its own button ever sends (a rejection), and requiring the same real permission every other sign-off in the system already checks. Approving a budget now only ever happens through the one screen built to do it properly.
A page could be read by someone who was not even signed in. One data-fetch built into the budget screen ran before the page checked whether anyone was logged in at all — not a wrong permission, no permission check whatsoever, for anyone with the address. Confirmed by actually doing it, signed out: the query still ran. No budgets exist yet on the live system, so nothing was actually exposed by this, but the door was open. Now closed.
Four more actions behind the same screen checked only “is someone logged in,” not “is this person allowed.” Creating, editing, deleting and reading a budget were all open to any signed-in account, leadership or not. All four now check the real permission — which, like the reports found in the last round, did not previously exist in the system's own rulebook at all and had to be added.
An approved budget could still be silently rewritten. The edit screen had no rule at all about what status a budget could be in to allow a change — a safeguard for exactly this already existed elsewhere in the system, written, correct, and simply never connected to this screen. It is now.

5Demonstration site

Still running at demo.vikundi.bjptechnologies.co.tz, on its own database, and still the proving ground for every module before it ships: every defect above, and every new endpoint, was verified there under real accounts — Admin, Secretary, Treasurer and an ordinary member — before being called finished. Member payouts specifically needed the treasurer's own account signed in, to confirm they are correctly refused a screen every other financial module in the app lets them use.
