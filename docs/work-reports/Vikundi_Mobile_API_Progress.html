1What changed since the last report

The last report covered condolences — the last screen an ordinary member touches often. Since then, two back-office modules are finished: the financial ledger (every member's savings standing side by side, plus the group's real available balance) and reconciliation (matching the imported M-Koba statement against the books, both for the whole group and for one member checking their own payments); and expenses and petty cash — recording group spending, the same review-then-approve sign-off already used for savings and condolences, and a fourth step neither of those needed: marking money as actually paid out, kept separate from merely being authorised.

The number that matters. Every screen a treasurer needs to run the books, both week to week and month to month, is now finished, deployed and documented — on top of every screen an ordinary member already had. 58 of roughly 117 planned doorways are finished. What is left is mostly things a group touches occasionally rather than routinely — budgets, one-off payouts, meetings, documents, elections, messaging — plus the settings screens an administrator rarely opens.

3Defects found in the existing system

The same pattern as every report so far: building each doorway means reading exactly how the web system enforces its rules, and that reading keeps finding places where it does not. This time, four — across the two modules — the most serious of which had no protection at all.

Any signed-in member could read the group's whole petty-cash list. The screen that feeds the petty-cash table its data had no permission check whatsoever — it only confirmed someone was logged in, not that they were allowed to see it. Every voucher's payee, amount and description was exposed to anyone with an account.

Confirmed by actually doing it, signed in as an ordinary member: the full voucher list came back, identical to what a treasurer sees.

Closed the same way as the same class of mistake in earlier reports: the screen now checks a real permission before answering, and that permission did not previously exist in the system's own rulebook at all — it was added, matching the rights the equivalent expenses screen already had, rather than invented from scratch.
Two reports a treasurer needs were silently unreachable by anyone except the two most senior roles. The financial ledger, the M-Koba reconciliation and the group's spending summary all check a permission that either did not exist in the system's rulebook at all, or existed but had never been granted to anyone. In practice this meant a Secretary or a Treasurer — not just the Chairperson or Admin — could be quietly refused a screen they are supposed to run. Fixed by adding the missing rule and the missing grants; nothing already configured was changed or removed.
A paid expense could still be silently edited. The rule guarding expense edits only blocked a change once an expense was “approved” — it did not also block one already marked “paid,” even though that money has already left the account. Fixed to block both.

4How the work is checked

Unchanged from every report so far, and still the standard every module is held to.

Checked against the group's own numbers, not just made up onesThe financial ledger's balance was cross-checked against the figure the home screen already shows for the same group, on the same server, at the same moment — two independently built screens agreeing is stronger proof than either one passing alone.
