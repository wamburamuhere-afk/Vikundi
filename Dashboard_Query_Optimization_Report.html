Dashboard Query Optimization

Cutting the number of database round-trips the dashboard makes on every load — same screen, far less work for the server.

The problem

Every time the dashboard loaded, it asked the database around 28 separate questions — many of them the same table, counted or summed several times, and one chart that queried the database twice for every month in a loop. Each question is a separate round-trip; the data itself is tiny, so the round-trips were the cost.

What we did

Ask the database fewer, smarter questions — let MySQL do the counting and grouping in one pass instead of PHP asking again and again.

PRChangeQueries
#3556-month trend chart — one GROUP BY month per series instead of a per-month loop12 → 2
#356Member counts (total / active / pending) — one conditional-aggregation query3 → 1
#357Each expense table read once (pending count + approved total together)4 → 2

Net effect: roughly half the round-trips, and the trend chart no longer gets slower as time goes on. No indexes, no caching, no schema changes — just better questions, so the numbers on screen are guaranteed identical.

Verified on the live site

Loaded the production dashboard after deploy — everything renders correctly and the figures stay internally consistent, with no console errors:

  • Members 327 / 327 active — the new one-pass member count.
  • Balance TSh 7,944,000 = Contributions 7,968,000 − Expenses 24,000 — the figures still reconcile exactly.
  • Contribution Trend chart renders — fed by the two grouped queries.
Live production dashboard, 27 Jul 2026 — after the three optimizations.

Outcome: the heaviest page in the system now does about half the database work per load, with zero change to what the group sees. The trend chart, member counts and expense totals all confirmed correct on production.
