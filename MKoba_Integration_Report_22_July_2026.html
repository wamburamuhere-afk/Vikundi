M-Koba Integration & Reconciliation

The group's real M-Koba records — the members, their savings history and every transaction — are now inside the system: shown the same way M-Koba shows them, reconcilable line-by-line, and ready to print or export.
Prepared for: Management Group: UKUU MSAKUZI Date: 22 July 2026 Status: Live & in use

1 · At a glance

The group keeps its money on M-Koba. The goal of this work was to bring that reality into the system — not a rough copy, but the real members and real money, shown exactly as they appear on the M-Koba statement, so leadership can reconcile the two with confidence whenever a question comes up. That is now done and in use.

2 · The real membership and their savings

The system had been running on sample data. It now holds the group's actual membership — 327 people — drawn from the M-Koba records, each matched to their own account. Their savings history (every payment, with its original date and receipt) was imported alongside them and matched to the right member automatically. Everything was backed up first, every figure checked, and the sensitive member file removed from the server once loaded.

3 · The system now shows what M-Koba shows Matching

Leadership asked for the transactions area to match the M-Koba statement exactly — the same columns, in the same order — so the two can be read side by side. It now does: reference number, receipt, date, member, member number, source, destination, amount and type all appear, just like on M-Koba. What used to be hidden (the reference and source details) is now fully visible.

4 · Reconciliation, made simple New

A dedicated reconciliation view holds the M-Koba statement next to the system's records and accounts for every single row — so nothing is unexplained. It clearly separates the money that is member savings from the money that is not (for example, group transfers between accounts, which should never count as members' savings):

5 · Trustworthy reference numbers Fixed

The problem. When an M-Koba statement is opened in a spreadsheet program (Excel), it quietly damages the long transaction reference numbers — turning something like a 16-digit reference into "3.8E+15". This is a spreadsheet quirk, not a system fault.

Fixed and future-proofed. The system now recovers a valid reference (from the receipt) for any that were already damaged, and — better still — it can now take the original M-Koba file directly, which keeps every reference number intact from the start. If a damaged file is ever uploaded, the system warns and explains how to avoid it. So the reference numbers can be trusted.

6 · Print and export that match Improved

  • The M-Koba statement can be printed — and it now prints sideways (landscape) so that all the columns fit on the page instead of being cut off.
  • It can also be exported to Excel in the very same M-Koba layout — ideal for handing to an auditor or checking against the original.
  • Small tidy-ups along the way: the phone and account numbers print cleanly, and the currency reads consistently as TSh throughout.

7 · Status & what's next

  • Everything above is built, tested and live on the system, checked against the group's real data, and protected by automated tests.
  • Ready for the future: because the system already matches M-Koba row-for-row and reconciles cleanly, it is well placed for the planned direct link with M-Koba down the line — today's work is the foundation for it, not throwaway.
  • When more history is available: loading additional M-Koba months is now a simple repeat — the system won't double-count.
In short: the group's M-Koba reality now lives in the system — the right members, the right money, shown M-Koba's way, fully reconcilable, and ready to print, export, and one day connect directly.
